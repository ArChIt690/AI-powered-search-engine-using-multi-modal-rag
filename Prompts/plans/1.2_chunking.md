# 1.2 Chunking (Smart, Semantic): plan

> Approved plan, kept for reference. Written against the v1 diagram; the Ingestion region is unchanged in v2.
> Later change: in 1.3, LangChain's `SemanticChunker` was replaced by our own splitter (same settings).

## Context
The diagram box is **"Spark Streaming: CHUNKING (Smart, Semantic)"**. It takes the `Document.sections` that the
1.1 loaders produce and turns them into `Chunk` objects (`schemas/chunk.py`). Those chunks are what gets embedded
(1.3), searched with BM25 and kNN, and passed to the LLM as context.

A first version exists in git (`6a6b474:Search_Engine/Data/chunking.py`). I will port it, and adapt it to what
1.1 now produces:
- **table sections** (`Section.kind="table"`, from PDFs)
- **video transcript sections**, each with a `timestamp`
- **CSV/JSON/XML records**, which should not overlap

Pictures (images, PDF charts, video frames) **do not go through Chunking**. In the diagram they go PICTURES →
Image Embeddings (CLIP), so their chunks are created in 1.3.

## Strategies, and which content gets which

| Content | Strategy | Why |
|---|---|---|
| **Prose**: .txt, Markdown sections, PDF page text | **Semantic** | Prose changes topic mid-page. Cutting where the meaning shifts keeps one idea per chunk, which gives cleaner embeddings and better search hits than a cut every 800 characters. |
| **Records**: CSV rows, JSON objects, XML elements | **Smart, record-aware** | Records have no "topic flow"; each one is a self-contained unit. Pack whole records into a chunk, and never cut one in half. |
| **Tables** (PDF, as Markdown) | **Smart, row-aware** | Split between rows, and **repeat the header row in every chunk**, so a chunk with `\|Bob\|78\|` still says `\|Name\|Score\|`. |
| **Video transcripts** | **Smart** (sections kept as they are) | 1.1 already groups Whisper output into sections of up to `chunk_size` characters, each with a start time. Splitting further would give the later pieces the wrong timestamp. |

`chunking_strategy` in config (`auto` / `smart` / `semantic`, already present):
- `auto` (default) = the table above
- `smart` / `semantic` force a strategy for prose, e.g. to compare them with the `eval/` benchmark.
  Tables, records and transcripts always use their own rule, because semantic splitting has nothing to work with in them.

## How each strategy works

**Smart**: LangChain `RecursiveCharacterTextSplitter`. It splits on the largest boundary that fits, in order:
paragraph/record, line, sentence (`. ? !`), clause (`; ,`), word, character. So:
- a paragraph stays whole unless it alone is longer than `chunk_size`
- sentences are never cut unless one sentence alone is too long

**Semantic**: LangChain `SemanticChunker` (from `langchain-experimental`, already a dependency).
1. Split the text into sentences, and embed each sentence together with its neighbours.
2. Compute the distance between consecutive sentences.
3. Cut where the distance is in the top 10% (`semantic_breakpoint_percentile = 90`).

Two safety nets from the old version:
- A semantic chunk longer than `chunk_size` is split again with Smart. One long topic can't make a
  3,000-character chunk, which would exceed what the embedding model reads well.
- A short last piece (under `semantic_min_chunk_size = 200`) is merged into the previous chunk, so there are no
  one-sentence stragglers.

**Big CSV/JSON/XML files are never one chunk.** Records are packed into chunks of up to `chunk_size` (800 chars):
- A 100,000-row CSV with ~80-char rows → ~10 rows per chunk → ~10,000 chunks.
- Each row is already self-describing (`name: Alice\ncity: Paris`, written by `structured.py`), so every chunk
  makes sense alone. No header repeat is needed.
- **One record bigger than 800 chars** (e.g. a large JSON object) is split at its field lines (`owner.name: …`),
  never mid-value. The record's **first line (usually its id) is repeated at the top of each piece**, so the pieces
  still say which record they belong to.
- Known limit, out of scope for 1.2: the 1.1 loaders read the whole file into memory before chunking. That's fine
  up to hundreds of MB. Streaming very large files record by record would be a loader change (1.1), not a chunking change.

**Overlap** (`chunk_overlap = 100` characters):
- **Smart prose**: yes. The last sentence of a chunk is repeated at the start of the next one, so an idea cut at a
  boundary is still findable.
- **Semantic cuts**: no. The cut is at a real topic change, so there's nothing to carry over.
- **Records, table rows, transcripts**: no. Repeating a CSV row or table row in two chunks would duplicate data
  in search results.

**Boundaries**: sections are grouped by (page, heading, timestamp, kind), and each group is chunked on its own.
So a chunk never mixes two PDF pages, two Markdown headings, two transcript sections, or a table with text.
That keeps each chunk's `page`, `section` and `timestamp` citation exact.

**Size unit**: characters (`chunk_size = 800`, about 200 tokens). That's well inside bge-small's 512-token
limit, and characters are what the loaders and config already use.

## Where the embedding model comes from
Semantic chunking needs a text embedding model, but that model is built in 1.3. So `chunk_document()` takes any
LangChain `Embeddings` object as an argument:
- **1.2 unit tests** pass a small fake one (one dimension per topic word), as the old tests did.
- **1.3** builds `TextEmbedder` (bge-small, a LangChain `Embeddings`), and the 1.6 pipeline passes that same
  instance to both Chunking and Text Embeddings, so the model loads once.
- If `auto` needs Semantic and no embeddings were given, it raises a clear error instead of silently switching to Smart.

## Implementation
**`src/search_engine/ingestion/chunking.py`**, one public function, which is the plain Python function behind
the Spark box (rule 3):
```python
def chunk_document(doc: Document, embeddings: Embeddings | None = None, settings: Settings | None = None) -> list[Chunk]
```
- Settings come from `core/config.py` (`chunking_strategy`, `chunk_size`, `chunk_overlap`,
  `semantic_breakpoint_percentile`, `semantic_min_chunk_size`). There are no new settings.
- It validates `0 <= overlap < chunk_size`.
- It groups the sections, then dispatches by kind (table / record / transcript / prose) to `_split_table`,
  `_split_records`, `_split_prose_smart` and `_split_prose_semantic`.
- Each `Chunk` gets `text`, `source`, `modality` (from `Document.modality`, e.g. `video_transcript`), `page`,
  `timestamp`, and `metadata = {"section": heading?, "content": "text" | "table" | "record"}`.
- Chunk ids, file type, dates and the rest are **not** set here. That's 1.4 Metadata Enrichment, as in the diagram.

**Reused**:
- The old chunker's splitter setup (separators list, `keep_separator="end"`) and `_merge_short_tail`
- `Section`, `SectionKind` and `Document` from `schemas/document.py`, and `Chunk` from `schemas/chunk.py`

**Tests**: `tests/unit/ingestion/test_chunking.py`, porting the 9 old tests and adding:
- a table split by rows, with the header repeated and no row cut
- records packed with no overlap; a large file giving many chunks, none over `chunk_size`
- an oversized record split at field lines, with its first line repeated in each piece
- transcript sections kept one-to-one, with their timestamps
- a chunk never mixing a table with page text
- `modality` and `timestamp` copied onto the chunks
