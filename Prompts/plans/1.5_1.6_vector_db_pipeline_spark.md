> Approved plan (2026-09-26). The user chose LangChain for everything Elasticsearch.

## 1.5 Vector Database (LangChain `langchain-elasticsearch`)
Two LangChain `ElasticsearchStore`s in the same Elasticsearch (one "ELASTICSEARCH / VECTOR DB" box). Each index is
created and managed entirely by LangChain, because a LangChain store handles one vector field per index.

| Store | Index | Holds | Vector | Query embedder |
|---|---|---|---|---|
| text store | `search_chunks_text` | text, table, record, transcript chunks | `text_embedding`, 384 (bge) | `TextEmbedder` |
| image store | `search_chunks_images` | image, chart, video-frame chunks | `image_embedding`, 512 (CLIP) | `ClipTextEmbeddings` (LangChain adapter around CLIP's text encoder) |

- `DenseVectorStrategy` + `num_dimensions`: LangChain creates the vector field.
- `metadata_mappings` generated from `ChunkMetadata` (+ modality, page, timestamp): typed metadata for filtering.
- `custom_index_settings`: English analyzer on `text`, for the BM25 half of LangChain's hybrid search (Part 2).
- Writes: `add_embeddings()` with the precomputed vectors and chunk ids; `modality`, `page`, `timestamp` go in `metadata`.
- Re-ingest: a file's old chunks are deleted by `doc_id` (through the store's client), then the new ones added.
- Index version: a Redis counter bumped after each successful write (Part 4 cache invalidation).
- Part 2 (not built here): LangChain hybrid search (`hybrid=True`) on the text store + kNN on the image store,
  fused with `EnsembleRetriever`; `EnsembleRetriever` is also the fallback if ES's built-in RRF returns 403 on the
  free license (checked in 1.5 against the local ES).

## 1.6 Pipeline and Spark Streaming
- `ingestion/pipeline.py`, `IngestionPipeline`: load → chunk → text embeddings → image embeddings → enrich →
  vector store, one shared bge model. `ingest_path(folder)` returns the report `cli.py` expects (files, chunks,
  skipped, failed); one bad file is counted, not fatal.
- PySpark Structured Streaming on `data/landing/`: one Spark stage per bold box in `streaming/jobs/`
  (text_extraction, extract_audio, chunking, text_embeddings, image_embeddings), each a thin `mapInPandas` wrapper
  around the tested function, models loaded once per worker; chained in one streaming query; each batch ends in
  Metadata Enrichment + the vector store write. Checkpoints in `data/checkpoints/`. Spark reads only file paths;
  `maxFilesPerTrigger` bounds batches.
- `search-engine ingest <path>` (one-off, native on Windows), `search-engine stream` (Spark).
- Spark service in `docker-compose.yml` from `docker/Dockerfile.spark` (Python 3.12, Java 17, PySpark, local mode);
  `data/` and the model cache mounted. Docker because Spark streaming on Windows needs Hadoop's `winutils.exe`.
- Build_order wording: "one stage per bold box" instead of "one job per bold box".

## Tests

- Integration (real ES + Redis from docker-compose, skipped if not running): write and read back through both

- E2E ("Done when"): drop txt/md/pdf/xml/csv/json/image/video into `data/landing/` with the Spark container running;
